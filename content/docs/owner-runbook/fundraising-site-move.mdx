# Move the Fundraising Site to Its Own Vercel Project

<Callout type="success" title="Done">
Checked 12 October 2026: `fundraising.josemadridsalsa.com` is attached to the
`josemadridsalsa-fundraising` Vercel project and its latest production deployment is Ready.
`fundraising.josemadrid.net` is on the same project and redirects (308) to
`fundraising.josemadridsalsa.com`. The fundraising site moved to the josemadridsalsa.com
address on 7 October (josemadridsalsa #577), so the addresses below use it. Keep this page for
reference, or if the project ever has to be rebuilt.
</Callout>

**Why:** the fundraising site and every fundraiser page (`/fundraising`, `/fundraisers/...`,
`/f/...`, the fundraiser portal, the arena) became their own app on 6 October 2026
(josemadridsalsa PR #563). The main site no longer serves those pages. Until
`fundraising.josemadridsalsa.com` is attached to a Vercel project that runs the new app, that
address shows the main site's home page instead of the fundraising site.

**Time:** about 30 minutes, most of it re-entering settings.

**You need:** Vercel owner access, and the original values for any setting marked
*Sensitive* in Vercel (see step 2).

<Callout type="info" title="Older project">
There is also an older Vercel project named `josemadrid-fundraising` from June 2026. Don't reuse
it unless its **Root Directory** is `apps/fundraising`; the live site runs on
`josemadridsalsa-fundraising`.
</Callout>

<Steps>
<Step>
### Create the project

1. Vercel → **Add New → Project**.
2. Import `jordolang/josemadridsalsa` (the same repository as the main site).
3. Name it `josemadridsalsa-fundraising`.
4. Set **Root Directory** to `apps/fundraising`. Leave **Include files outside the root
   directory** switched on.
5. Leave the framework, build command and install command as Vercel fills them in; they come
   from `apps/fundraising/vercel.json`.
6. Don't deploy yet if Vercel offers to. If it deploys anyway, that's fine; it will fail or
   be incomplete until step 2 is done, and nobody sees it.
</Step>

<Step>
### Copy the settings

The two sites share the database, sign-in, payment, email and upload settings.

1. Open the main project: **josemadridsalsa → Settings → Environment Variables**, filtered to
   **Production**.
2. In the new project, **Settings → Environment Variables**, add the same names with the same
   values for **Production**.
   - Values marked **Sensitive** can't be revealed or copied out of Vercel. Paste them again
     from where they came from (BigCommerce API account, Square, the shipping provider, and so on).
   - The `POSTGRES_*` values come from a database integration. Under **Storage** (or
     **Integrations**) in the new project, connect the **same** database rather than typing them.
   - If a developer has the Vercel CLI set up, `vercel env pull` on the main project and
     **Import .env** on the new one saves typing for the non-sensitive values.
3. In the **fundraising** project, set these three. Don't copy them from the main project;
   they say which address each site lives at:

| Setting | Value in the fundraising project |
|---|---|
| `NEXT_PUBLIC_SITE_URL` | `https://www.josemadridsalsa.com` (the main site) |
| `NEXT_PUBLIC_FUNDRAISING_SITE_URL` | `https://fundraising.josemadridsalsa.com` |
| `NEXTAUTH_URL` | `https://fundraising.josemadridsalsa.com` |

   The main project needs no change here; it already defaults to these addresses.

4. **Deployments → Redeploy** the new project's latest deployment so it picks the settings up.
</Step>

<Step>
### Add the sign-in callbacks

Accounts are shared, but each site signs people in on its own address, so each sign-in provider
needs the fundraising address added (keep the main site's entries):

| Provider | Where | Add |
|---|---|---|
| Google | Google Cloud console → APIs & Services → Credentials → the OAuth client | `https://fundraising.josemadridsalsa.com/api/auth/callback/google` |
| Facebook | developers.facebook.com → the app → Facebook Login → Settings → Valid OAuth Redirect URIs | `https://fundraising.josemadridsalsa.com/api/auth/callback/facebook` |
| Apple | developer.apple.com → Services ID → Return URLs | `https://fundraising.josemadridsalsa.com/api/auth/callback/apple` |

Skip any provider the site doesn't use.
</Step>

<Step>
### Move the domain

1. **josemadridsalsa → Settings → Domains**: remove `fundraising.josemadridsalsa.com` if it is
   there.
2. **josemadridsalsa-fundraising → Settings → Domains**: add `fundraising.josemadridsalsa.com`.
3. Still in the fundraising project, add `fundraising.josemadrid.net` with **Redirect to**
   `fundraising.josemadridsalsa.com`, **308**, so old links keep working.

The site is unavailable for the minute between removing and adding.
</Step>

<Step>
### Check it

- [ ] `https://fundraising.josemadridsalsa.com` shows the fundraising site, not the salsa store home page.
- [ ] `https://fundraising.josemadrid.net` lands on `https://fundraising.josemadridsalsa.com`.
- [ ] `https://www.josemadridsalsa.com/fundraising` lands on `https://fundraising.josemadridsalsa.com/fundraising`.
- [ ] A fundraiser's page opens.
- [ ] The fundraiser portal sign-in works.
- [ ] Open a fundraiser referral link, add a jar and go to checkout: checkout stays on the
      fundraising site.
- [ ] In the portal, uploading a group logo works.
</Step>
</Steps>

## If it goes wrong

Move `fundraising.josemadridsalsa.com` back to the `josemadridsalsa` project. That restores the
current state (main site's home page on that address); a developer then has to revert PR #563 to
bring the old fundraiser pages back on the main project.

## What stays on the main site

Staff still manage fundraisers in the main admin, the fundraiser phone app still talks to the
main site, and every webhook (Stripe, PayPal, Square, BigCommerce) still points at the main
site. Nothing about those changes here.
